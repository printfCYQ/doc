# 设计模式

设计模式是前人踩坑总结出来的"代码组织套路"。不是语法，是**在常见场景下，怎么把类/对象搭得松耦合、好扩展、易维护**。1994 年 GoF（Gang of Four）那本书归纳了 23 种，分成三类：创建型（管对象怎么生）、结构型（管对象怎么组合）、行为型（管对象之间怎么协作）。

先说一句大实话：**别为了用模式而用模式**。小项目硬套模式反而绕。先写出能跑的代码，发现"这里老要改、这里老要加类"，再用模式化掉痛点。

---

## 〇、SOLID 五大原则（比模式更根本）

模式是招式，原则是内功。写之前先记住：

- **S 单一职责**：一个类只干一件事。改 A 原因不该影响 B。
- **O 开放封闭**：对扩展开放、对修改封闭。加功能尽量新增类，别改老代码。
- **L 里氏替换**：子类能替父类，且行为不崩。别在子类里违背父类约定。
- **I 接口隔离**：别逼客户实现用不到的方法。大接口拆小。
- **D 依赖倒置**：依赖抽象（接口），不依赖具体类。高层不依赖低层细节。

后面的模式，大多是在落地这五个原则。

## 一、创建型（5 种）——对象怎么创建

### 1. 单例（Singleton）
**意图**：一个类全局只有一个实例。
**场景**：配置中心、连接池、日志器。
```java
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}  // 私有构造，防外面 new
    public static Singleton getInstance() {
        if (instance == null) {                 // 双重检查锁定，线程安全又高效
            synchronized (Singleton.class) {
                if (instance == null) instance = new Singleton();
            }
        }
        return instance;
    }
}
```
**坑**：反射/序列化能破单例；多例（如每个线程一个）别硬用单例。

### 2. 工厂方法（Factory Method）
**意图**：把"new 哪个类"推迟到子类决定。
**场景**：一个方法要造不同产品，但产品种类以后会变。
```java
interface Product { void use(); }
class A implements Product { public void use() { System.out.println("A"); } }
class B implements Product { public void use() { System.out.println("B"); } }

abstract class Creator {
    abstract Product create();   // 工厂方法，子类决定造 A 还是 B
    void doWork() { create().use(); }
}
```

### 3. 抽象工厂（Abstract Factory）
**意图**：造"一族"相关产品（如 Windows 按钮+文本框、Mac 按钮+文本框配套）。
**场景**：需要保证一组对象风格一致（跨平台 UI 套件）。
**坑**：加一个新种类产品要改所有工厂接口，违反开闭原则。

### 4. 建造者（Builder）
**意图**：一步步拼出复杂对象，避免构造函数参数爆炸。
**场景**：一个对象有很多可选字段（如 HTTP 请求、订单）。
```java
Order order = new Order.Builder()
    .setItem("书").setCount(2).setGift(true).build();
```

### 5. 原型（Prototype）
**意图**：通过"复制自己"来创建对象，而不是 new（省去昂贵初始化）。
**场景**：创建成本高、且新对象大多是已有对象的变体。`clone()` 就是这思路。
**坑**：浅拷贝 vs 深拷贝容易踩（引用字段没复制就共享了）。

## 二、结构型（7 种）——对象怎么组合

### 6. 适配器（Adapter）
**意图**：把不兼容的接口"转接头"成客户要的接口。
**场景**：老系统接口和新系统对不上，如读 SD 卡要个 TF 转 SD 卡套。
```java
class OldApi { void specificRequest() {...} }
interface Target { void request(); }
class Adapter implements Target {
    private OldApi old = new OldApi();
    public void request() { old.specificRequest(); }  // 包一层
}
```

### 7. 桥接（Bridge）
**意图**：把"抽象"和"实现"拆成两条独立的继承轴，各自扩展不互相影响。
**场景**：形状（圆/方）× 颜色（红/蓝）这种"两个维度各自变化"。
**好处**：不用为"红圆、蓝圆、红方、蓝方"写 4 个类，2+2 组合就行。

### 8. 组合（Composite）
**意图**：让"单个对象"和"对象容器"用同一套接口，递归地当树处理。
**场景**：文件系统（文件 vs 文件夹）、UI 组件树。
```java
interface Node { void render(); }
class File implements Node { public void render() {...} }
class Folder implements Node {
    List<Node> children = new ArrayList<>();
    public void render() { for (Node n : children) n.render(); }  // 递归
}
```

### 9. 装饰器（Decorator）
**意图**：不改动原类，动态地给对象加功能（一层套一层）。
**场景**：IO 流（`BufferedReader` 套 `FileReader`）、给咖啡加奶加糖。
```java
Reader r = new BufferedReader(new FileReader("a.txt"));  // 套娃加缓冲
```
**坑**：套太多层，调试时看不出到底是谁的错。

### 10. 外观（Facade）
**意图**：给一堆复杂子系统包一个简单入口。
**场景**："一键下单"背后调库存、支付、物流三个系统，客户只调一个 `order()`。
**好处**：客户不依赖子系统细节，降耦。

### 11. 享元（Flyweight）
**意图**：大量细粒度对象共享内部状态，省内存。
**场景**：文本编辑器里每个字符的位置（外部状态）不同，但字体字形（内部状态）可共享。
**坑**：区分"内部可共享 / 外部不可共享"状态是关键。

### 12. 代理（Proxy）
**意图**：给对象加个"替身"，控制访问。
**场景**：远程代理（RPC 桩）、虚拟代理（懒加载大图）、保护代理（权限校验）。
```java
class RealImage { void display() {...} }      // 加载很慢
class ProxyImage implements RealImage {
    RealImage real;                            // 用到才真的 new
    void display() { if (real == null) real = new RealImage(); real.display(); }
}
```

## 三、行为型（11 种）——对象怎么协作

### 13. 责任链（Chain of Responsibility）
**意图**：请求沿一条链传，谁合适谁处理，处理完可停可继续。
**场景**：审批流（组长→经理→总监）、过滤器链（Web 中间件）。
```java
interface Handler { void handle(Request r, Handler next); }
```

### 14. 命令（Command）
**意图**：把"请求"封装成对象，能排队、撤销、记录日志。
**场景**：遥控器按钮、事务回滚、操作历史（Ctrl+Z）。
**好处**：发起者和执行者解耦，可参数化地传"要做的事"。

### 15. 解释器（Interpreter）
**意图**：为某种文法定义解释器，按规则求值。
**场景**：规则引擎、表达式计算（如 `a > 1 && b < 2`）。
**联动**：和[编译原理](../principle/principle.md)的 AST 执行是一回事。

### 16. 迭代器（Iterator）
**意图**：不暴露集合内部结构，就能挨个遍历元素。
**场景**：你天天用——`for (x of list)`、`list.iterator()` 就是它。JDK 已内置。

### 17. 中介者（Mediator）
**意图**：一堆对象互相引用乱成一团，抽个"中介"统一协调，谁也别直接找谁。
**场景**：聊天室（消息经服务器转发）、GUI 控件联动。
**坑**：中介者容易变成"上帝类"啥都管。

### 18. 备忘录（Memento）
**意图**：不破坏封装地保存/恢复对象之前的状态。
**场景**：编辑器撤销、游戏存档。

### 19. 观察者（Observer）
**意图**：一个对象状态变，自动通知一堆依赖它的对象。
**场景**：事件总线、发布订阅、MV* 框架的数据绑定。`addEventListener` 就是观察者。
```java
subject.subscribe(observer);   // 订阅
subject.notify();              // 状态变了，所有观察者被通知
```

### 20. 状态（State）
**意图**：对象行为随内部状态变，且状态可多到要单独成类。
**场景**：订单状态（待付→已付→发货→完成）、电梯运行/停止/故障。
**好处**：把 `if (state == X)` 一大串换成各状态类，清爽。

### 21. 策略（Strategy）
**意图**：把"可互换的算法"抽出成独立类，运行时选一个。
**场景**：排序算法切换、支付方式（微信/支付宝/银行卡）选一个。
```java
interface PayStrategy { void pay(int money); }
class Order { PayStrategy s; void checkout() { s.pay(100); } }
```

### 22. 模板方法（Template Method）
**意图**：父类定好算法骨架，留几个步骤给子类填。
**场景**：冲泡饮料（烧水→冲泡→倒杯，冲泡步骤子类定：茶 vs 咖啡）。
```java
abstract class Drink {
    final void make() { boil(); brew(); pour(); }  // 骨架固定
    abstract void brew();                            // 子类填
}
```

### 23. 访问者（Visitor）
**意图**：把"对元素的操作"从元素类里抽出来，新增操作不用改元素类。
**场景**：编译器遍历 AST 做不同检查（类型检查、优化），元素不动只加访问者。
**坑**：加新元素类型要改所有访问者，反向违反开闭——和抽象工厂类似的两难。

## 四、怎么选，别乱套

| 你想解决 | 优先考虑 |
|---------|---------|
| 对象创建太散、种类多变 | 工厂方法 / 抽象工厂 / 建造者 |
| 接口对不上 | 适配器 |
| 动态加功能 | 装饰器 |
| 子系统太复杂 | 外观 |
| 一对多通知 | 观察者 |
| 算法可替换 | 策略 |
| 状态驱动行为 | 状态 |
| 审批/过滤链 | 责任链 |
| 撤销/重做 | 命令 / 备忘录 |

**反模式提醒**：
- 一个 if-else 就能解决，别上来就抽象工厂
- 单例别当全局变量筐，啥都往里塞
- 观察者订阅了记得取消，否则内存泄漏
- 装饰器、责任链套太深，排错时找不到北

## 五、新手最常踩的坑

1. **为模式而模式**：5 行代码能解决的硬拆成 5 个类 3 个接口。
2. **单例写成全局变量**：啥状态都塞单例，测试时互相污染。
3. **策略/状态分不清**：策略是"选算法"，状态是"状态决定行为且会自动流转"。
4. **观察者忘了注销**：页面销毁了监听还在，内存泄漏、重复触发。
5. **过度依赖继承实现结构型**：组合（has-a）往往比继承（is-a）灵活，桥接/装饰器就是教这个。
6. **忽视 SOLID 只背模式**：背下 23 种不如吃透 SOLID，模式是原则的具体招。

## 六、练习

1. 用**策略模式**改写一段"根据支付方式算手续费"的 if-else 代码。
2. 用**装饰器模式**实现"给一条消息依次加 时间戳、加前缀[INFO]、加密"三种包装，顺序可换。
3. 用**观察者模式**写一个"温度超过 30 度自动通知风扇和空调"的小程序。
4. 单例的"双重检查锁定"里，为什么 `instance` 要加 `volatile`？（提示：指令重排）
5. 模板方法和策略都能"换步骤/算法"，区别在哪？各适合什么场景？

---

## 七、速查口诀

- SOLID：单一、开闭、里氏、接口隔离、依赖倒置（内功）
- 创建型：单例唯一、工厂延后、建造者拼装、原型复制、抽象工厂出一套
- 结构型：适配器转接头、桥接双轴、组合成树、装饰套娃、外观简化、享元共享、代理替身
- 行为型：责任链传递、命令封装、观察者通知、策略可换、状态流转、模板定骨架、访问者外挂操作
- 别为模式而模式，痛点来了再用

## 八、学习路线

1. SOLID 原则（本章〇，先内功）
2. 创建型 5 种（一）
3. 结构型 7 种（二）
4. 行为型 11 种（三，观察者/策略/状态最常用）
5. 选型与反模式（四、五）
6. 进阶：读《Head First 设计模式》（图多好懂）或 GoF 原书，然后在自己项目里"发现"模式而不是"强塞"
