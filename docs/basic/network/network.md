# 计算机网络

计算机网络可以理解为"怎么让两台机器互相说话"。你刷网页、发微信、看视频，背后都是一套分层协议在忙活。

打个比方：你（应用）要寄一封信（数据）给朋友。你只管写内容交给前台（应用层），前台装信封、写地址（传输层+网络层），邮局分包运（链路层+物理层），对方前台拆信交给朋友。你不用管路上卡车怎么开——这就是"分层"的意义：**每层只管自己的事，层与层之间定好接口**。

这篇把最常被问到的几块讲透：**分层模型、网络层（IP/子网）、传输层（TCP/UDP）、应用层（HTTP/DNS）**。

---

## 一、为什么分层，分几层

网络太复杂，不分层没法维护。两套模型：

### OSI 七层（理论模型，记概念用）
```
7 应用层      HTTP、FTP、DNS、SMTP
6 表示层      加密、压缩、编码
5 会话层      建立/维护/断开会话
4 传输层      TCP、UDP（端到端）
3 网络层      IP、路由（主机到主机）
2 数据链路层   MAC、交换机、ARP（相邻节点）
1 物理层      网线、光纤、电信号（比特流）
```

### TCP/IP 四层（实际用的）
```
应用层（含 OSI 5/6/7）
传输层（TCP/UDP）
网际层（IP）
网络接口层（链路+物理）
```

面试一句话：**OSI 是教科书模型，实际互联网跑的是 TCP/IP 四层。** 平时说"七层""四层"都行，重点是理解每层干什么。

### 数据怎么走：封装
发数据时**从上往下每层加头**：应用数据 → 加 TCP 头（段）→ 加 IP 头（包）→ 加 MAC 头（帧）→ 比特流发出。收数据时**从下往上逐层拆头**。每层只认自己那层的头。

## 二、网络层：IP 与寻址

### IP 地址
每台联网设备有个 IP。现在两套：
- **IPv4**：32 位，形如 `192.168.1.10`，约 43 亿个，早不够用了
- **IPv6**：128 位，形如 `2001:db8::1`，数量大到给地球上每粒沙分配都够

### 子网掩码与子网划分
IP 不能乱发，得知道"目标在不在本地网"。**子网掩码**告诉哪部分是"网络号"、哪部分是"主机号"。

例：`192.168.1.10` / `255.255.255.0`（写成 `192.168.1.10/24`）：
- 前 24 位是网络号 `192.168.1`
- 后 8 位是主机号，这网里能容纳 2^8 - 2 = 254 台（去掉全 0 网络地址和全 1 广播地址）

**CIDR**（无类域间路由）就是这种 `IP/数字` 的写法，`/24` 表示掩码 255.255.255.0。

### 私有地址与 NAT
`192.168.x.x`、`10.x.x.x`、`172.16-31.x.x` 是**私有地址**，内网随便用，出不了公网。你家路由器用一个**公网 IP** 对外，家里几十台设备通过 **NAT（网络地址转换）** 共用它上网——这就是为什么 IPv4 不够也能撑到现在。

### ARP 与路由
- **ARP**：知道对方 IP 但不知道 MAC（物理地址）时，广播问"谁是这个 IP"，对方回 MAC。局域网内靠它。
- **路由**：跨网段时，数据包交给**路由器**转发。路由器看目标 IP 的网络号，查路由表决定下一跳。

### ICMP
"网络层的侦察兵"。`ping` 用的就是 ICMP 回显请求/应答；`traceroute` 靠它看路径上经过哪些路由器。

## 三、传输层：TCP（重点）

TCP 是**可靠、面向连接、字节流**的协议。Web、邮件、文件传输都靠它。

### 报文里关键的东西
- **端口号**：IP 找主机，端口找主机里的哪个程序（HTTP 80、HTTPS 443、MySQL 3306）
- **序列号 / 确认号**：保证数据不乱、不丢、不重
- **窗口大小**：流量控制用

### 三次握手（建立连接）
```
客户端                          服务端
  SYN, seq=x        →
                   ←  SYN, ACK, seq=y, ack=x+1
  ACK, ack=y+1      →
```
为什么三次？**双方的发送和接收能力都要确认**。两次不够（服务端不知道客户端能不能收），三次刚好。第三次可能丢，但丢了服务端会重发，客户端已认为连上了。

### 四次挥手（断开连接）
```
客户端                          服务端
  FIN, seq=u        →   (客户端：我不发了)
                   ←  ACK, ack=u+1   (服务端：知道，但我可能还有数据要发)
                   ←  FIN, seq=v     (服务端：我也发完了)
  ACK, ack=v+1      →   (客户端：收到，等 2MSL 后彻底关闭)
```
为什么四次不是三次？因为 TCP 是**全双工**，关闭要两边各自说"我不发了"。服务端收到 FIN 后可能还有数据要传，所以 ACK 和 FIN 分两次发。最后客户端等 **2MSL**（报文最大生存时间的两倍）是为了：确保最后一个 ACK 到达；让旧连接的残留报文在网络里消失，不会串到新连接。

### 可靠传输怎么实现
- **超时重传**：发了对面没确认，定时重发
- **确认应答（ACK）**：收到就回确认
- **滑动窗口**：不必一个一个等确认，一口气发一批（窗口大小内），提高效率
- **按序到达 + 去重**：序列号保证

### 拥塞控制（别把网络挤爆）
流量控制是"怕接收方撑爆"，拥塞控制是"怕整个网络堵死"。四个阶段：
1. **慢启动**：先发 1 个，每收到确认窗口翻倍（指数涨），快速探路
2. **拥塞避免**：到阈值后改成线性涨（每次 +1），稳一点
3. **快重传**：收到 3 个重复 ACK，不等超时立刻重发丢失的包
4. **快恢复**：重传后窗口不回到 1，而是减半继续

### 粘包问题
TCP 是字节流，没有消息边界。发送端连发 "AB""CD"，接收端可能一次读到 "ABCD"（粘包），也可能分两次 "AB""CD"（拆包）。**解决：应用层自己定边界**——定长、分隔符、或"长度字段+内容"。

## 四、传输层：UDP

UDP 是**不可靠、无连接、数据报**的协议。发了就不管，不握手、不重传、不保序。

| | TCP | UDP |
|---|-----|-----|
| 连接 | 有（三次握手） | 无 |
| 可靠 | 是（重传/确认） | 否 |
| 速度 | 较慢（有开销） | 快 |
| 顺序 | 保证 | 不保证 |
| 场景 | 网页、邮件、文件 | 视频通话、游戏、DNS、直播 |

**UDP 用在"丢一点无所谓、但卡一下要命"的场景**：视频通话丢几帧还能看，但等重传就画面冻结了。

## 五、应用层：HTTP

HTTP 是 Web 的基石，客户端（浏览器）发请求，服务端回响应。

### 一个请求/响应长啥样
```
GET /index.html HTTP/1.1      ← 请求行：方法 路径 版本
Host: www.example.com         ← 请求头
User-Agent: ...
                              ← 空行
(可选请求体)

HTTP/1.1 200 OK               ← 状态行：版本 状态码 原因
Content-Type: text/html       ← 响应头
                              ← 空行
<html>...</html>              ← 响应体
```

### 常见方法
- `GET`：取资源（参数在 URL，有长度限制，能被缓存/收藏）
- `POST`：提交数据（参数在 body，更安全，不缓存）
- `PUT` / `DELETE`：更新 / 删除（RESTful 风格常用）
- `HEAD` / `OPTIONS` / `PATCH` 等

### 状态码（记住区间）
- **2xx 成功**：200 OK、201 Created
- **3xx 重定向**：301 永久、302 临时、304 没改（用缓存）
- **4xx 客户端错**：400 参数错、401 未登录、403 没权限、404 找不到、429 太多请求
- **5xx 服务端错**：500 内部错、502 网关坏、503 过载、504 网关超时

### Cookie 与 Session
HTTP 本身**无状态**（每个请求互不相认）。要记住"你是谁"：
- **Cookie**：服务端通过响应头 `Set-Cookie` 让浏览器存一小段数据，之后每次请求自动带上。存在客户端。
- **Session**：服务端存用户状态（存在服务器内存/Redis），给客户端一个 SessionID（通常放 Cookie 里）。存在服务端。

简单说：Cookie 是"会员卡（你揣着）"，Session 是"后台档案（店里存着，凭卡号查）"。

### HTTPS / TLS
HTTP 明文传输，被人抓包就全看见了。HTTPS = HTTP + **TLS 加密**。
- 握手阶段用**非对称加密**协商出一个对称密钥
- 之后用**对称加密**传数据（快）
- 还有**证书**机制防止"中间人冒充"（CA 机构背书）

## 六、HTTP/1.1 vs 2 vs 3

| 版本 | 关键改进 | 痛点 |
|------|---------|------|
| HTTP/1.1 | 持久连接（一个 TCP 连多次请求）、管线化 | **队头阻塞**：一个请求慢，后面排队；每请求重复头部 |
| HTTP/2 | **多路复用**（一个连接并发多个流）、头部压缩、二进制帧 | 仍有 TCP 层队头阻塞 |
| HTTP/3 | 底层换 **QUIC（基于 UDP）** | 解决 TCP 队头阻塞，弱网下更快 |

**队头阻塞**通俗讲：一列火车，头节车厢出事，后面全堵。HTTP/1.1 在应用层堵，HTTP/2 在 TCP 层还可能堵，HTTP/3 直接绕开 TCP 用 UDP+QUIC。

## 七、DNS（域名解析）

你输入 `www.example.com`，机器只认 IP，得先翻译成 `93.184.x.x`。**DNS** 干这个。

解析过程（简化）：
```
浏览器缓存 → 系统缓存(/etc/hosts) → 本地 DNS 服务器
  → 根DNS(.) → 顶级域DNS(.com) → 权威DNS(example.com) → 拿到 IP
```
- **递归查询**：本地 DNS 替你一路问到底
- **迭代查询**：根/顶级域 DNS 只告诉你"下一步问谁"，你自己接着问

## 八、WebSocket

HTTP 是"请求-响应"，服务端不能主动推。聊天、实时行情需要**全双工长连接**，用 **WebSocket**：先通过 HTTP 握手升级协议，之后连接一直开着，双方随时互发，不用每次带头部开销。

---

## 九、新手最常踩的坑

1. **把 TCP 当消息边界**：`send("AB")`、`send("CD")` 对面可能一次收 "ABCD"。应用层自己分包。
2. **三次握手和四次挥手记反**：握手写数据前，挥手断连接；挥手多一次是因为服务端可能还有数据要发。
3. **以为 HTTPS 绝对安全**：证书被信任链、或用了弱密码套件仍有风险；HTTPS 防窃听不防钓鱼。
4. **混淆端口和进程**：一个端口同一时刻只能一个进程监听；两个服务抢 8080 会 "address already in use"。
5. **忽略 TIME_WAIT / 2MSL**：频繁短连接服务端可能端口不够用，别急着关连接或盲目重用。
6. **子网算错**：`/24` 不是 256 台可用，要减 2（网络地址和广播地址）。
7. **UDP 当 TCP 用**：指望它重传保序，结果丢包乱序。该用 TCP 别省。

## 十一、速查口诀

- OSI 七层、TCP/IP 四层，实际跑四层
- 数据发送层层加头，接收层层拆头
- IP 找主机、端口找程序；私有地址靠 NAT 出公网
- TCP 可靠三次握手四次挥手，UDP 快但不保证到
- 握手三次确认双向能力，挥手四次因为全双工
- 可靠靠确认+重传+滑动窗口，拥塞靠慢启动+避免+快重传
- HTTP 无状态，Cookie 在客户端、Session 在服务端
- 1.1 队头阻塞、2 多路复用、3 换 QUIC
- DNS 把域名翻成 IP，WebSocket 双向长连
